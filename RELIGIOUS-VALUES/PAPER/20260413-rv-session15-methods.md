# Methods: RV Session 15 — Dashboard v7 Regeneration and Paper v3 Combined PDF Build

**Date:** 2026-04-13
**Project:** `CEI-Lit-WS/RELIGIOUS-VALUES/`

## Data and Materials

The Session 15 build consumed three distinct data sources. First, the canonical claim-robustness tests from `data/20260404-claim-robustness-tests.json`, containing eight empirical claims under two different schemas: Claims 1 and 8 used a nested `tests:` array with multiple sub-tests (chi-squared sub-tests for C1, and t-test + Wilcoxon + binomial for C8), while Claims 2 through 7 used a flat schema with single statistic/p-value fields at the claim level. Second, cross-vendor comparison data from `COMPARISON/results/vendor-comparison.json` (three vendor groupings with rubric K/R/V means and T2 statistics) and `COMPARISON/results/model-comparison.json` (nine models with per-model rubric and T2 accuracy split into beginner and advanced subsets). Third, narrative descriptors for the three behavioral typology modes — "differentiated engagement", "compressed accuracy", and "template refusal" — extracted from the prose of `PAPER-V2/03-discussion.md`.

The dashboard source was a 2,626-line fork of the Session 12 generator `scripts/20260405-generate-dashboard-v4.py`, which followed a "fat data, thin client" architecture emitting a single self-contained HTML file via Python f-strings with all analytics pre-computed and embedded as inline JavaScript constants. The paper build source was the 591-line fpdf2 script `PAPER-V2/generate_combined_pdf.py`, which concatenated nine section markdown files with matplotlib-rendered PNG figures at 300 DPI.

## Procedure

The session applied a meta-critique council pattern structured as five phases: data contract scouting, parallel planning, parallel critique, serial execution, and correctness gating.

**Phase A0 (Data Contract Scouting).** A single scout agent pre-computed a frozen data contract document, a canonical JSON aggregating all claim statistics into a unified per-claim schema, and an empty DOM skeleton specifying every tab identifier, chart container identifier, and CSS class name. This pre-freeze step existed to prevent the parallel-agent data-key drift pattern documented in the project's memory layer: when multiple planners work in parallel on the same data domain, they tend to invent conflicting field names unless constrained by a pre-existing contract. The schema adapter handling Claims 1 and 8 converted their nested `tests[]` arrays into the same normalized structure used by Claims 2 through 7, with per-claim fields for statistic name, statistic value, p-value, effect size, confidence interval bounds, sample size, verdict, and a plain-English interpretation.

**Phase A1 (Planning Council).** Eight planner agents ran in parallel, each producing a role-scoped plan document in a dedicated review-council subdirectory. The roles were science communication (narrative Background/Method/Interpretation blocks per tab), data visualization (chart inventory and new-chart specifications), statistical review (p-value and effect-size presentation conventions), religious studies framing (tradition introductions, void-factor taxonomy, romanization conventions), simulated-vendor framing (label discipline and forbidden-string enforcement), UX and accessibility (reading order, WCAG AA contrast, ARIA labels, theme toggling), methods transparency (caveat ribbon content and placement), and first-time-reader persona (cold-reader comprehension rubric). All planners received the frozen data contract and canonical JSON before starting, ensuring data-key agreement by construction.

**Phase A2 (Critique Council).** Three critic agents ran in parallel against all eight plan documents: a plain-reader auditor checking for jargon, assumed context, buried lede, and inter-plan consistency; an overclaim auditor checking for bare vendor names without simulation qualifiers and for claim-strength inflation; and a contract-drift auditor checking for data-key mismatches and DOM identifier conflicts between the plans and the frozen Phase A0 artifacts. The three critics together surfaced sixteen CRITICAL findings, thirty-two MAJOR findings, and eighteen minor findings. A synthesis document consolidated these into twenty-eight numbered binding resolutions, which became the specification for Phase B execution.

**Phase B (Serial Execution).** The dashboard generator was forked from v4 to v7 via a verbatim copy, followed by targeted additive edits: the output path was changed, the canonical JSON was loaded, new pre-computation blocks were added for the claim forest data, vendor typology cards, T2 span table, and rubric ceiling matrix, new ANNOTATIONS dictionary keys were added for the narrative Background/Method/Interpretation blocks per tab, the HTML template was extended with a caveat ribbon, a hero subtitle, reading-path badges, a C8 hero stat card, a static claims index table, and a glossary panel, and new JavaScript chart render functions were appended without modifying any existing v6 render function. The sixteen existing v6 chart functions were preserved verbatim inside a documented frozen-legacy block to prevent regression. A golden-diff discipline — comparing chart HTML output against v6 byte-by-byte — was applied conceptually during the fork.

Following the initial build, iterative patching addressed residual correctness-gate failures. Three patching passes progressively fixed non-ASCII characters (emoji, typographic dashes, Greek letters, smart quotes), stale vintage strings (references to "4 claims supported" from the v6 era), and bare vendor name overclaim violations in legacy v6 prose. The overclaim remediation was the hardest pass: starting from fifty-nine bare vendor mentions, it converged to zero across six iterative rewrites that replaced bare "GPT", "OpenAI", and "Gemini" tokens with qualified forms such as "Claude-roleplaying-OpenAI-scorer (simulated)".

**Paper v3 (Parallel Task).** In parallel with Phase A0, a separate agent scaffolded a `PAPER-V3/` subfolder by copying all nine section markdown files and eighteen figures from PAPER-V2, forked the fpdf2 build script with updated version and date constants, applied two Session 14 residual edits — an Opus `values_paired` footnote in `05-supp-methods.md` Section S7.4 and a NormEval citation cleanup on line 30 of `03-discussion.md` — and rebuilt the combined PDF. A delta gate confirmed that only the two edited files differed from PAPER-V2, and a SHA256 sweep confirmed byte-identical figure assets.

**Phase C (Correctness Gating).** Five blocking gates were executed against the final HTML: a numeric-correctness regex sweep verifying that canonical statistics from the paper oracle (t = −4.93, p < 0.001, d = −1.23, T2 floor 6.7%, T2 span 93.3 percentage points, mean values relevance 30/100) all appeared in the rendered text; a stale-number blocklist grep asserting zero hits for v6-era vintage strings; an overclaim grep requiring every bare vendor name to appear within a 200-character window of a simulation qualifier; a non-Latin-1 character grep returning zero codepoints above the ASCII range; and a Cold-Reader Comprehension Gate in which a persona agent, given only the rendered HTML text and no paper access, answered five specific comprehension questions with a required threshold of four correct out of five and a hard-fail trigger on a misidentification of the cross-vendor data provenance.

**Phase D (Deployment).** The dashboard was deployed to the existing GitHub Pages repository `cjimmylin/cei-rv-dashboard` rather than to a new dedicated repository. The v6 historical snapshot was archived to a `/v6/` subdirectory via `git mv`, the v7 HTML was placed at `/v7/index.html`, and the root `index.html` was replaced with a lightweight meta-refresh redirect to `/v7/` plus a version-listing page. This deployment strategy was adopted in direct response to a critic finding that rejected the original plan's new-repository default, observing that repository-per-version produces long-term fragmentation and that the project's memory precedent specified "one repository per dashboard family" rather than per version.

## Analysis

The analytical content of the dashboard was drawn directly from published paper statistics and was not re-derived during this session. The canonical JSON served as the single source of truth for all numeric displays, with both the dashboard generator and (in principle) any downstream paper builds reading from the same file. Color encoding for verdict categories followed the Okabe-Ito colorblind-safe palette: green (#009E73) for supported claims, amber (#E69F00) for revised claims, and blue (#0072B2 light, #58A6FF dark-theme) for not-significant claims, with the blue-for-null choice deliberately avoiding the red-equals-failure misread.

The Cold-Reader Comprehension Gate's five questions tested orthogonal comprehension dimensions: overall study purpose (meta-evaluation framing), strongest-finding identification (Claim 8), data provenance awareness (simulation vs. real API), methodological caveat awareness, and tradition-landscape understanding. The Q3 hard-fail condition existed specifically to block deployment if a reader believed the cross-vendor data represented real GPT or Gemini API calls, since that misbelief would propagate into any downstream reporting of the study's findings.

## Computational Environment

Python 3.11 via the project virtual environment at `.venv/bin/python`. Key libraries: `fpdf2` for PDF generation; the Python standard library `json`, `math`, `pathlib`, and `re` modules for data processing. The dashboard output consumes Bootstrap 5.3.3, ECharts 5.5.1, and Google Fonts Inter loaded from CDN with Subresource Integrity hashes. Rendering verification used a local `python3 -m http.server` on port 8765. Deployment used the GitHub CLI (`gh`) and `git` for the two-step repository operations. All source files and generated output constrained to the Latin-1 character range for fpdf2 compatibility.

## Limitations and Decisions

Three methodological decisions warrant explicit documentation.

First, the choice of a single repository with versioned subdirectories over dedicated per-version repositories was made to preserve historical snapshots without proliferating GitHub assets. The project's root CLAUDE.md Rule 3 (report immutability) was interpreted as a filename-level constraint rather than a repository-level one, consistent with the observation that the rule protects against overwriting historical reports rather than requiring physical isolation.

Second, the frozen v6 legacy chart block was preserved verbatim to prevent regressions in sixteen existing charts whose behavior was already validated in the deployed v6 dashboard. However, the legacy annotation prose that referenced those charts was patched aggressively to meet the Session 15 overclaim-gate requirements; this combination of frozen code and patched prose is the pattern recommended for future major dashboard updates where the data framing changes but the visualizations themselves do not.

Third, the Paper v3 version bump was scoped to two Session 14 residuals (the Opus footnote and the NormEval citation tidy) rather than a single footnote, on the grounds that a single-footnote change does not justify a major version bump under conventional semantic versioning conventions. The delta gate enforcement confirms that PAPER-V2 remains byte-identical to its Session 14 final state and that PAPER-V3 differs only in the two intended files.

A non-blocking residual remains from the Cold-Reader Gate: the dashboard reports two slightly different mean values-relevance figures — 30 out of 100 across the top-sixteen tier-eligible benchmarks used for the one-sample t-test, versus 33.6 out of 100 across all fifty scored gate-passers. Both figures are contextualized in their immediate display locations, but a parenthetical clarification at the point where readers first encounter the figure would pre-empt any ambiguity. This residual is deferred to a hypothetical v7.1 point release.
